# РОЗДІЛ 1. АНАЛІЗ ПРЕДМЕТНОЇ ОБЛАСТІ ТА ПОСТАНОВКА ЗАДАЧІ ДОСЛІДЖЕННЯ

## 1.1 Актуальність вибраної теми дослідження

Проблема харчових відходів залишається актуальним інженерним викликом для сектору HoReCa та роздрібної торгівлі: галузеві оцінки фіксують втрати до 6% обороту через списання товарів з обмеженим терміном придатності. Наявні цифрові рішення для перерозподілу надлишкової продукції (Too Good To Go, GoodMeal) орієнтовані виключно на бік споживача та не усувають операційного бар'єра з боку постачальника — ручного фотографування, опису і внесення кожної одиниці залишків у систему адміністративним персоналом закладу в умовах обмеженого часу наприкінці зміни. Це формує supply-side friction, що обмежує масштабованість подібних платформ.

Інженерна складність проєкту визначається необхідністю забезпечити низьку затримку (latency) обробки запитів мобільного застосунку персоналу закладу за умови асинхронної, потенційно повільної операції розпізнавання зображень через зовнішній Vision API, а також відмовостійкість (fault tolerance) системи до пікових навантажень наприкінці робочих змін закладів-постачальників. Розв'язання цих задач вимагає архітектурного відокремлення синхронного шляху обробки HTTP-запитів від асинхронної обробки задач комп'ютерного зору за допомогою черги повідомлень, кешування агрегованих аналітичних метрик та проєктування контрактної мікросервісної взаємодії через REST API з незалежним B2C-модулем.

## 1.2 Огляд сучасних підходів до вирішення відповідних завдань

Розв'язання задачі потребує поєднання п'яти груп архітектурних і алгоритмічних підходів. Кожна з них розглядається нижче з позиції впливу на затримку, відмовостійкість і вартість супроводу.

### 1.2.1 Розпізнавання товарів на зображеннях

Для автоматизованої ідентифікації об'єктів на зображеннях застосовуються два підходи. Перший передбачає спеціалізовані моделі комп'ютерного зору, навчені на розміченому наборі класів і розгорнуті локально або на пристрої (edge-інференс): такий підхід забезпечує детерміновану затримку та незалежність від мережі, проте потребує розміченого навчального набору для кожного класу й супроводу конвеєра донавчання. Другий підхід передбачає мультимодальні моделі загального призначення, доступні через зовнішній API (OpenAI Vision, Google Gemini Vision): вони не потребують навчання під конкретний каталог і приймають довільний набір позицій, проте характеризуються змінною затримкою відповіді, вартістю кожного запиту, залежністю від провайдера та недетермінованістю результату. Остання властивість зумовлює необхідність валідації структурованого виходу за схемою та використання порога впевненості з ручним виправленням. Для системи з нефіксованим асортиментом закладів доцільним є другий підхід.

### 1.2.2 Асинхронна обробка ресурсомістких операцій

Тривала операція, зокрема виклик зовнішнього Vision API, виконується поза циклом обробки HTTP-запиту. За патерном Producer–Consumer API-сервіс (producer) ставить завдання в чергу, а фоновий обробник (consumer) виконує його незалежно від клієнтського з'єднання; клієнт отримує підтвердження прийняття (HTTP 202 Accepted) і далі отримує статус завдання асинхронно. Черга на основі Redis (BullMQ) забезпечує повторні спроби з експоненційною затримкою, обмеження швидкості та горизонтальне масштабування споживачів. Семантика доставки at-least-once вимагає ідемпотентних споживачів, а довговічність завдань залежить від налаштувань персистентності Redis (RDB/AOF).

### 1.2.3 Кешування аналітичних агрегатів

Агреговані показники (відновлений дохід, кількість врятованих товарів, динаміка продажів) обчислюються над історичними даними, обсяг яких зростає з часом. Патерн cache-aside із зберіганням результатів у Redis та обмеженим часом життя запису (TTL) знижує навантаження на реляційну БД. Компромісом є eventual consistency показників у межах TTL, що допустимо для аналітичних екранів і недопустимо для транзакційних операцій, де джерелом істини залишається PostgreSQL.

### 1.2.4 Контрактна інтеграція незалежних модулів

Незалежні B2B- та B2C-модулі взаємодіють за версійованим контрактом REST API (специфікація OpenAPI 3.1, формат JSON) і мають окремі логічні схеми баз даних. Такий підхід зменшує зв'язність і дозволяє виконувати та тестувати модулі окремо, проте вимагає узгодження версій контракту та перевірки його сумісності під час інтеграційного тестування.

### 1.2.5 Структура серверного застосунку

Серверна частина організовується за N-Tier-архітектурою (рівні представлення, бізнес-логіки та доступу до даних) із використанням модульної структури NestJS та впровадження залежностей (dependency injection). Наскрізна типізація TypeScript на backend і в мобільному застосунку (React Native) зменшує вартість супроводу контрактів даних між клієнтом і сервером.

## 1.3 Аналіз та порівняння існуючих рішень на ринку готових програмних продуктів

Для порівняльного аналізу обрано три програмні системи, що вирішують суміжні задачі: Too Good To Go (Business-платформа для закладів-постачальників) та Flashfood як прямі аналоги у сфері перерозподілу товарів з обмеженим терміном придатності, а також Winnow Vision як опосередкований аналог, що застосовує комп'ютерний зір для обліку харчових відходів. Аналіз обмежено інженерними параметрами: архітектурний патерн, протоколи взаємодії, стек даних і механізми консистентності, Technical Bottlenecks.

Жодна з систем не має публічної архітектурної документації. Аналіз ґрунтується на непрямих джерелах: технічних вимогах вакансій, публікаціях галузевих видань та заявах засновників. Кожне твердження супроводжується маркером достовірності: [П] — підтверджено прямим публічним джерелом; [Н] — непряме свідчення, що не гарантує поточного production-стану; [–] — не підтверджено публічними джерелами; [Г] — аналітична гіпотеза, виведена з бізнес-моделі або типових практик для систем цього класу. Дата звернення до всіх веб-джерел: 30.09.2026.

### 1.3.1 Too Good To Go

**Архітектура та масштабованість.** [П] Backend реалізовано як Spring Boot 3 Application на Java 25, що працює в Kubernetes у multi-region розгортанні на AWS; технічна команда налічує понад 90 осіб [1]. [П] За даними компанії, платформа обслуговує 133 млн зареєстрованих користувачів і 261 тис. партнерів у 21 країні [1]. [Н] Вимоги вакансії містять досвід із Domain-Driven Design та Clean/Hexagonal Architecture, що вказує на шарову організацію коду всередині сервісів [1]. [–] Модульний моноліт чи набір мікросервісів публічно не підтверджено. Kubernetes у multi-region конфігурації забезпечує горизонтальне масштабування stateless-обчислювального шару та регіональну відмовостійкість.

**Протоколи взаємодії.** [–] REST API, gRPC, GraphQL, WebSockets, а також протокол інтеграції з POS/ERP партнерів публічно не підтверджено. [Н] Асинхронна взаємодія реалізується через брокери повідомлень: вимоги вакансії містять Message Systems, AWS SQS та SNS [1].

**Стек даних і консистентність.** [Н] Вимоги вакансії містять MySQL, Redis, Elasticsearch та AWS S3 [1]. [–] Топологія БД, механізми консистентності (Outbox, Saga, idempotency keys, optimistic locking) і стратегія кешування не підтверджені. За аналітичною оцінкою [Г], атомарне резервування пакета реалізується умовним оновленням у MySQL або optimistic locking за версією запису; пошуковий індекс Elasticsearch оновлюється асинхронно, що зумовлює eventual consistency лічильника доступних пакетів. Усі положення цього абзацу залежать від припущення, що MySQL та Elasticsearch використовуються в production.

**Technical Bottlenecks [Г].** Конкуренція за гарячий запис (Consistency, Throughput) виникає при одночасному резервуванні обмеженої кількості пакетів, яку задає партнер. Write-консистентність реляційної БД у multi-region (Consistency, Latency) зумовлена реплікацією між регіонами та затримкою запису у віддалений primary-регіон. Лаг індексу пошуку (Consistency) призводить до відображення пакета, якого вже немає, і відмови на етапі резервування.

### 1.3.2 Flashfood

**Архітектура та масштабованість.** [П] Платформа складається зі споживацького та ритейлерського застосунків; ритейлерський інтегровано з ручними сканерами, які використовують працівники магазинів [5]. [Н] Вимоги вакансії Staff Full-Stack Engineer: TypeScript, Node.js (Express, Koa, Fastify), React та Next.js, Go для backend-сервісів, Docker і Kubernetes, хмара AWS/GCP/Azure як рівнозначні варіанти [2]. [Н] Вакансії Tech Lead та Senior Front End містять React Native в екосистемі Expo, а також Kotlin і Swift [3, 4]. Поєднання Node.js та Go вказує на polyglot-архітектуру сервісів (інтерпретація). [–] Архітектурний патерн (моноліт, мікросервіси, event-driven) і конкретний хмарний провайдер не підтверджено.

**Протоколи взаємодії.** [–] REST, GraphQL, gRPC, WebSockets і протокол обміну зі сканерами не підтверджено. [П] Інтеграція із системами ритейлерів існує; формати обміну (API, файли, EDI) не розкриті [5]. [Н, слабка достовірність] GraphQL, Kafka та Airflow згадано у вакансії лише як "nice to have" [2].

**Стек даних і консистентність.** [Н] Вимога проєктувати моделі даних для реляційних і NoSQL БД без назв конкретних СУБД [2]. [–] Кешування, черги та механізми консистентності не підтверджені. За аналітичною оцінкою [Г], інтеграція з гетерогенними системами ритейлерів реалізується пакетною синхронізацією (файли CSV/SFTP або періодичне опитування API), оскільки legacy-системи рідко підтримують вихідні webhooks; кількість пропозиції зменшується атомарно при покупці.

**Technical Bottlenecks [Г].** Застарілі дані про залишок (Consistency) виникають, коли інтервал синхронізації перевищує швидкість розпродажу товару в магазині. Нормалізація даних різних ритейлерів (Throughput, вартість розробки) потребує окремого адаптера для кожного формату каталогів і штрихкодів. Піковий трафік у вікна нових пропозицій (Latency, Throughput) виникає при одночасному навантаженні пошуку та кошика в межах однієї геозони.

### 1.3.3 Winnow Vision

Основне джерело даних — публікація Computer Weekly від 14.06.2019 [6]; поточний стан реалізації не підтверджено [–].

**Архітектура та масштабованість.** [П] Система є edge-cloud гібридом: цифрові ваги під стандартним баком, камера та вбудована система на NVIDIA Jetson TX2. Інференс виконується на пристрої: нейронна мережа зіставляє об'єкт із відомими видами харчових відходів [6]. [П] Мотивація edge-підходу — нестабільне інтернет-з'єднання на кухнях [6]. [П] Цикл навчання: у разі невпевненого розпізнавання персонал вводить тип відходів вручну, дані асинхронно вивантажуються в AWS, де модель донавчається на GPU NVIDIA V100 із TensorFlow [6]. [П, заява вендора] Заявлено розпізнавання понад 1 000 типів їжі [7]. [П, заява компанії, 2019] Понад 80% відходів розпізнається коректно [6]. [–] Серверну декомпозицію бекенду не підтверджено. Інференс розподілено по пристроях, тому хмарні витрати на нього не зростають разом із кількістю об'єктів; складність переходить в управління флотом пристроїв і конвеєр донавчання.

**Протоколи взаємодії.** [П] Канал пристрій → хмара використовує асинхронне вивантаження даних; конкретний протокол (MQTT, HTTPS, gRPC) не підтверджено [–] [6]. [П] Для телеметрії розроблено власний код, оскільки AWS не відповідав потребам [6]. [–] Публічний API не підтверджено; зовнішня аналітика подається через Winnow Hub і звіти [7]. За аналітичною оцінкою [Г], телеметрія передається по HTTPS зі схемою store-and-forward, а оновлення моделі доставляються pull-моделлю.

**Стек даних і консистентність.** [П] TensorFlow для навчання; у 2019 році потрібно до 1 000 зображень на кожен вид їжі [6]. [Н, вторинне джерело] Навчальний набір понад 500 млн зображень відходів [8]. [–] СУБД, сховище зображень і механізми консистентності між edge і хмарою не підтверджені. За аналітичною оцінкою [Г], для доставки at-least-once використовується ідемпотентний прийом подій із унікальним ідентифікатором, що генерує пристрій.

**Technical Bottlenecks.** [П] Оновлення та моніторинг розподіленого парку embedded-пристроїв становлять окрему інженерну проблему [6]. [П] Точність залежить від обсягу розмічених даних на кожен клас; ручне виправлення виконує функцію fallback [6]. [Г] Вартість апаратного забезпечення на масштабі тисяч локацій; неоднорідні версії моделі при частково розгорнутому оновленні (Consistency).

### 1.3.5 Аналітичний висновок

Аналіз аналогів показує, що жоден із них не охоплює одночасно автоматизацію B2B-продажів і розпізнавання інвентарю засобами комп'ютерного зору. У розглянутих джерелах для Too Good To Go та Flashfood CV-інференс не згадується, тому якість даних про залишки, імовірно, визначається ручним введенням партнера або синхронізацією із системами ритейлера. Winnow Vision реалізує розпізнавання, але як edge-cloud гібрид: інференс виконується на NVIDIA Jetson TX2, а модель донавчається в AWS на GPU V100 [6]. Підтверджені обмеження стосуються Winnow: апаратна прив'язка та необхідність керування флотом пристроїв і оновленням моделі ускладнюють застосування цього підходу як програмного сервісу для закладів харчування; за аналітичною оцінкою, це супроводжується капітальними витратами на кожну локацію. Архітектура Too Good To Go (Spring Boot 3 на Java 25 у Kubernetes, multi-region AWS) підтверджена [1], проте її надмірність для очікуваного навантаження B2B-системи є аналітичною оцінкою, а не встановленим фактом. Решта слабких місць також належать до аналітичних оцінок. За аналітичною оцінкою, імовірними вузькими місцями є конкуренція за гарячий запис при резервуванні обмеженої кількості одиниць, write-консистентність реляційної БД у multi-region і лаг пошукового індексу (Too Good To Go), а також застарілі дані про залишок при пакетній синхронізації та нормалізація каталогів різних ритейлерів (Flashfood). Їхня вага знижується тим, що технології MySQL, Redis та Elasticsearch для Too Good To Go підтверджуються лише непрямими джерелами, а патерн моноліт/мікросервіси та протоколи не підтверджені для жодного з аналогів.

Обраний стек вирішує ці проблеми частково, і його доцільно розглядати як зменшення ризиків, а не як їх усунення. Модульна N-Tier-структура NestJS із залежностями через ін'єкцію та наскрізна типізація TypeScript на backend і в мобільному застосунку (React Native) зменшують вартість інтеграції та супроводу порівняно з імовірно polyglot-платформою Flashfood (Node.js та Go). Асинхронна обробка зображень за патерном Producer-Consumer на BullMQ відокремлює HTTP-запит від тривалого виклику зовнішнього Vision API, забезпечує повторні спроби з відступом, обмеження швидкості та горизонтальне масштабування споживачів. Джерелом істини про стан інвентарю є PostgreSQL з ACID-транзакціями. Умовні оновлення або optimistic locking за версією запису дозволяють, імовірно, уникнути overselling без залежності від eventually consistent вторинного індексу для критичних операцій. Redis кешує аналітичні агрегати й розвантажує реляційне сховище, а REST API (JSON) із контрактною інтеграцією обмежує зв'язність із незалежним B2C-модулем. Водночас рішення аналогів мають переваги. Керований брокер SQS/SNS (за непрямими даними, використовується в Too Good To Go) забезпечує довговічність повідомлень із реплікацією між зонами доступності, тоді як черга BullMQ залежить від налаштувань персистентності Redis (RDB/AOF), і при відмові вузла без реплікації можлива втрата завдань. Edge-інференс Winnow за аналітичною оцінкою переважає хмарний Vision API за вартістю одного запиту та за незалежністю від мережі й лімітів провайдера, тоді як у проєкті вартість лінійно зростає з обсягом зображень, а недетермінованість відповіді універсальної моделі вимагає валідації результату.

Ці компроміси компенсуються архітектурними заходами, які визначають вимоги до Розділу 2. Щодо довговічності черги передбачено налаштування AOF та реплікації Redis, патерн Transactional Outbox у PostgreSQL як джерело істини для повторної постановки невиконаних завдань, а також ідемпотентні споживачі з детермінованим ідентифікатором завдання (BullMQ гарантує доставку щонайменше один раз). Щодо Vision API передбачено валідацію структурованого виходу за схемою, поріг впевненості з ручним виправленням як fallback (за аналогією з механізмом Winnow), кешування результатів за хешем зображення та пакетну обробку для зниження вартості. Залишкові обмеження цими заходами не усуваються: змінна вартість запиту, залежність від зовнішнього провайдера, експлуатація в межах одного регіону (multi-region відмовостійкість у кваліфікаційній роботі не передбачена) та непідтверджена точність універсальних моделей на довгому хвості класів. Тому їх необхідно перевіряти експериментально, а проєктні рішення щодо ідемпотентності, транзакційної узгодженості черги й БД та обробки невпевнених розпізнавань є предметом Розділу 2.

## 1.4 Аналіз обраної предметної області в межах дослідження (модель As-Is)

### 1.4.1 Загальна характеристика домену

Предметною областю є операційна діяльність закладів харчування (кафе, пекарні, ресторани) у частині реалізації продукції з обмеженим терміном придатності через цифрові платформи перерозподілу товарів. Домен охоплює три взаємопов'язані контури: формування торгових пропозицій (лотів) із залишків продукції, приймання та видачу замовлень, оформлених покупцем через B2C-маркетплейс, а також облік фінансових показників відновленого доходу. Розроблювана система є B2B-модулем, що взаємодіє з незалежним B2C-модулем за контрактом REST API; обидва модулі виконуються в межах окремих кваліфікаційних робіт і мають власні бази даних.

Встановлено, що станом на 2026 рік на домен впливають такі технологічні тенденції: застосування мультимодальних моделей комп'ютерного зору, доступних через API, для розпізнавання об'єктів на зображеннях; перехід інструментів персоналу на мобільні платформи; використання черг повідомлень і асинхронної обробки для ізоляції ресурсомістких операцій від синхронного шляху обробки запитів; контейнеризація та автоматизація доставки (CI/CD). Системи-аналоги (Too Good To Go, Flashfood, Winnow Vision) розглянуто в підрозділі 1.3; у розглянутих публічних джерелах не підтверджено поєднання розпізнавання зображень із формуванням торгових пропозицій закладу.

### 1.4.2 Ключові актори та сутності системи

Визначено такі актори:

- **Адміністратор закладу** — керує меню, категоріями та лотами, переглядає фінансову аналітику, керує обліковими записами персоналу.
- **Касир** — підтверджує видачу замовлень шляхом сканування QR-коду.
- **Покупець (B2C-клієнт)** — зовнішній актор; оформлює замовлення на маркетплейсі та пред'являє QR-код при отриманні.
- **B2C-модуль** — зовнішня система; отримує опубліковані лоти та передає дані про замовлення через REST API.
- **Зовнішній сервіс комп'ютерного зору** (OpenAI Vision API або Google Gemini Vision) — автоматизований актор; повертає перелік розпізнаних позицій.

Базовими інформаційними сутностями є: заклад, користувач із роллю, позиція меню, категорія, лот, смарт-бандл, зображення, завдання розпізнавання зі статусом, замовлення, QR-токен видачі, агрегований показник аналітики.

### 1.4.3 Бізнес-процеси та потоки даних (As-Is)

**Процес 1. Формування торгової пропозиції (лота).** Наприкінці зміни персонал вручну фотографує залишки продукції, вносить назву, опис, категорію, кількість, ціну та інтервал видачі через адміністративну панель платформи; кожна одиниця оформлюється окремим циклом введення. Потік даних має вигляд «пристрій персоналу → форма → API платформи → база даних». Встановлено такі вузькі місця (bottlenecks): трудомісткість процесу зростає лінійно з кількістю позицій, а доступний час обмежений кінцем зміни, тому частина залишків не публікується (supply-side friction); опис позицій є неструктурованим і залежить від людського фактору; публікація лота на B2C-маркетплейсі потребує окремого внесення даних за відсутності єдиного контракту обміну. Окремою інженерною проблемою за аналітичною оцінкою є пряме синхронне використання зовнішнього Vision API з обробника HTTP-запиту: затримка відповіді визначається провайдером, а пік запитів наприкінці зміни призводить до вичерпання пулу з'єднань і перевищення таймаутів (Latency, Availability). Потік даних за такого використання має вигляд «мобільний застосунок → API → зовнішній Vision API → база даних» без проміжної черги повідомлень.

**Процес 2. Видача замовлення покупцю.** За відсутності програмної верифікації персонал підтверджує видачу за усним номером замовлення або екраном застосунку покупця. За аналітичною оцінкою, вузькими місцями є відсутність журналу видач із фіксацією факту видачі, ризик помилкової або повторної видачі та розбіжність станів замовлення між B2C- і B2B-модулями (Consistency). Факт видачі не може бути верифікований постфактум. Потік даних має вигляд «B2C-клієнт → B2C-модуль → REST API → B2B-модуль → екран персоналу»; зворотне оновлення статусу замовлення з B2B- у B2C-модуль за відсутності єдиного контракту виконується вручну або не виконується.

**Процес 3. Облік та фінансова аналітика.** Показники відновленого доходу та кількості врятованих товарів формуються вручну або обчислюються агрегувальними запитами до транзакційної бази даних при кожному відкритті звіту. Затримка (Latency) такого запиту зростає з обсягом історичних даних, а виконання агрегації конкурує за ресурси з транзакційним навантаженням (Throughput). Повторне обчислення незмінних історичних показників є надлишковим. Потік даних має вигляд «транзакційна база даних → агрегувальний запит → екран звіту» без проміжного кешу.

### 1.4.4 Регуляторні та індустріальні обмеження

- **Захист персональних даних:** Закон України «Про захист персональних даних» та Регламент (ЄС) 2016/679 (GDPR) — під час обробки даних персоналу, покупців і випадкового потрапляння осіб до кадру зображень.
- **Безпека та якість харчових продуктів:** вимоги Закону України «Про основні принципи та вимоги до безпечності та якості харчових продуктів» щодо термінів придатності та маркування продукції, яка реалізується за зниженою ціною; збереження історії лотів і видач підтримує прослідковуваність.
- **Безпека веб-сервісів і мобільних застосунків:** OWASP API Security Top 10 та OWASP Mobile Top 10; автентифікація за OAuth 2.0 / OpenID Connect.
- **Обмін даними:** REST API за специфікацією OpenAPI 3.1, формат JSON, дата й час за ISO 8601.
- **Використання зовнішніх AI-сервісів:** передавання зображень стороннім провайдерам потребує мінімізації даних і визначення строку їх зберігання; результат розпізнавання є недетермінованим і потребує валідації.

### 1.4.5 Обґрунтування необхідності автоматизації

Виявлені вузькі місця визначають три напрями автоматизації. По-перше, лінійна залежність трудомісткості формування лота від кількості позицій усувається перенесенням розпізнавання на сервер із поверненням чернетки лота, яку персонал лише підтверджує. По-друге, залежність затримки API від зовнішнього Vision API усувається ізоляцією виклику в черзі фонових задач із повторними спробами. По-третє, відсутність верифікації видачі та повторне обчислення аналітики усуваються одноразовими QR-токенами з журналом видач і кешуванням агрегатів. Для кожного напряму в підрозділі 1.5 сформульовано функціональні вимоги та вимірювані метрики.

## 1.5 Постановка задачі та формування вимог (модель To-Be)

### 1.5.1 Концептуальна модель To-Be

Цільова модель передбачає заміну ручного введення й прямих синхронних викликів зовнішніх сервісів мікросервісною B2B-системою (N-Tier backend на NestJS, REST API, PostgreSQL, Redis, BullMQ) із мобільним застосунком на React Native для адміністраторів і касирів.

Процес формування лота трансформується таким чином: працівник виконує фотографування вітрини або залишків у мобільному застосунку; зображення передається на сервер, де завдання розпізнавання ставиться в чергу BullMQ (шаблон Producer–Consumer), а клієнт одразу отримує підтвердження прийняття (HTTP 202) і асинхронно відстежує статус. Фоновий обробник передає зображення до Vision API, перевіряє структурований результат за схемою та формує чернетки лотів і смарт-бандлів; позиції з достовірністю нижче порога виносяться на ручне виправлення. Підтверджені лоти публікуються на B2C-маркетплейсі через REST API за спільним контрактом. Ізоляція виклику Vision API від HTTP-шляху усуває залежність часу відповіді API від латентності провайдера, а повторні спроби з експоненційною затримкою підвищують відмовостійкість під час пікових навантажень.

Процес видачі трансформується таким чином: покупцю видається QR-код із одноразовим токеном; касир скануює його камерою телефону, система перевіряє токен та статус замовлення, фіксує видачу в журналі та узгоджує стан із B2C-модулем. Повторне використання токена блокується.

Процес аналітики трансформується таким чином: агреговані показники обчислюються асинхронно та кешуються в Redis за патерном cache-aside із обмеженим TTL; екран аналітики читає готові агрегати, що знімає навантаження з PostgreSQL.

### 1.5.2 Функціональні вимоги (Core Features)

**Модуль розпізнавання та формування лотів (Snap & Sell)**

- Приймати фотографію вітрини або залишків від мобільного застосунку, ставити завдання розпізнавання в чергу BullMQ із асинхронним поверненням статусу, розпізнавати товарні позиції через OpenAI Vision API або Google Gemini Vision із валідацією структурованого результату за схемою та генерувати чернетки лотів із можливістю ручного виправлення.
- Генерувати смарт-бандли (комбіновані пропозиції) на основі розпізнаних позицій.

**Модуль каталогу**

- Виконувати CRUD-операції над меню, категоріями та лотами закладу.

**Модуль автентифікації та доступу**

- Автентифікувати користувачів та розмежовувати права за рольовою моделлю (адміністратор закладу, касир).

**Модуль замовлень та видачі**

- Генерувати QR-коди замовлень з одноразовим токеном і підтверджувати видачу скануванням із фіксацією у журналі.

**Модуль фінансової аналітики**

- Обчислювати та відображати показники відновленого доходу, кількості врятованих товарів і динаміку продажів із кешуванням агрегатів у Redis.

**Модуль інтеграції**

- Публікувати лоти та синхронізувати стан замовлень з B2C-модулем через спільний REST API-контракт (OpenAPI 3.1).

### 1.5.4 Постановка задачі

Таким чином, метою кваліфікаційної роботи є проєктування та розробка мікросервісної B2B-інформаційної системи з асинхронною обробкою завдань розпізнавання зображень для вирішення задачі автоматизації формування торгових пропозицій закладів харчування, підтвердження видачі замовлень та обліку фінансових показників у межах платформи перерозподілу товарів з обмеженим терміном придатності. Передбачено реалізацію REST API на Node.js (NestJS) з PostgreSQL, Redis і чергою BullMQ та мобільного застосунку на React Native; встановлено цільові показники: p95 ≤ 200 мс при 500 RPS, автентифікація за OAuth 2.0 / OIDC, RPO ≤ 24 год.

## Висновки до розділу 1

Проведений аналіз встановив, що наявні платформи перерозподілу продукції з обмеженим терміном придатності орієнтовані переважно на бік споживача, а операційний бар'єр постачальника — ручне формування кожної пропозиції наприкінці зміни — залишається не вирішеним. У розглянутих публічних джерелах Too Good To Go та Flashfood не згадують розпізнавання зображень, а Winnow Vision реалізує його як edge-cloud гібрид, що потребує апаратної прив'язки до локації та керування парком пристроїв. Аналіз процесів As-Is виявив три групи вузьких місць: трудомісткість ручного введення, що зростає лінійно з кількістю позицій; ризик залежності затримки API від зовнішнього Vision API за синхронного виклику; відсутність програмної верифікації видачі та надлишкове повторне обчислення аналітичних агрегатів. Слабкі місця аналогів і описаних процесів належать до аналітичних оцінок, окрім випадків, позначених у підрозділі 1.3 як підтверджені публічними джерелами.

Обраний шлях вирішення передбачає відокремлення синхронного шляху обробки HTTP-запитів від виклику Vision API за допомогою черги BullMQ (Producer–Consumer), збереження стану в PostgreSQL як джерела істини, кешування аналітичних агрегатів у Redis та контрактну інтеграцію з B2C-модулем через REST API. Стек NestJS і TypeScript із мобільним застосунком на React Native зменшує вартість супроводу контрактів даних. Водночас хмарний Vision API поступається edge-інференсу за вартістю запиту та незалежністю від мережі, а довговічність черги залежить від налаштувань персистентності Redis; ці компроміси компенсуються повторними спробами, ідемпотентними споживачами, порогом впевненості з ручним виправленням і резервним копіюванням, зафіксованими у вимогах підрозділу 1.5. Сформульовано сім функціональних вимог і матрицю нефункціональних вимог із числовими метриками, перевірюваними під час тестування.

Аналітичне обґрунтування та вимоги, сформульовані в Розділі 1, є вхідними даними для наступних етапів. Проєктування архітектури (діаграми UML і C4 Model, ER-модель бази даних, специфікація REST API-контракту з B2C-модулем, рішення щодо ідемпотентності та транзакційної узгодженості черги й бази даних) становитиме предмет Розділу 2, а безпосередня технічна реалізація функціональних вимог, інструментальний аудит коду та розгортання — предмет Розділу 3.
