# ADR-001: Вибір черги фонових задач для асинхронного розпізнавання зображень

- **Статус:** Approved (Затверджено)
- **Дата:** 2026-11-08
- **Пов'язані вимоги:** [SRS-FUN-03](../srs.md#srs-fun-03), [SRS-NFR-PERF-03](../srs.md#srs-nfr-perf-03), [SRS-NFR-PERF-04](../srs.md#srs-nfr-perf-04), [SRS-NFR-REL-01](../srs.md#srs-nfr-rel-01), [SRS-NFR-REL-02](../srs.md#srs-nfr-rel-02), [SRS-NFR-REL-06](../srs.md#srs-nfr-rel-06), [SRS-NFR-SCAL-01](../srs.md#srs-nfr-scal-01)
- **Пов'язані діаграми:** [C4 Container](../2_design.md#21-контекстне-та-контейнерне-моделювання-системи-c4-model), [C4 Component](../2_design.md#22-компонентне-моделювання-критичного-сервісу-системи)

## Context

Розпізнавання зображення через Vision API виконується за час, який визначає зовнішній провайдер (SRS-NFR-PERF-04 допускає до 10 с на виклик). Синхронне виконання в HTTP-обробнику суперечить SRS-NFR-PERF-03 (відповідь 202 Accepted з p95 ≤ 1000 мс) і за піку наприкінці зміни вичерпує пул з'єднань API (підрозділ 1.4.3).

Обмеження, що накладає SRS:

- до 3 повторних спроб з експоненційною затримкою (початкова затримка 2 с, множник 2) і черга dead-letter (SRS-NFR-REL-01);
- ідемпотентна обробка (SRS-NFR-REL-02);
- горизонтальне масштабування до 4 обробників із пропускною здатністю не нижче 3,5 від одного (SRS-NFR-SCAL-01);
- стан завдання зі значеннями `queued`, `processing`, `completed`, `failed`, `needs_review` (SRS-FUN-03, SRS-FUN-04);
- розгортання на одному вузлі, без керованих хмарних сервісів і без реплікації інфраструктури.

Оцінка навантаження: пік — одночасне надходження зображень від кількох закладів наприкінці зміни (орієнтир SRS-NFR-PERF-03: 20 одночасних завантажень). Пропускна здатність черги не є обмежувальним чинником: Vision API обробляє одне зображення за секунди, а BullMQ на одному екземплярі Redis обробляє тисячі завдань за секунду за малого розміру payload.

## Alternatives

| № | Варіант | Переваги | Обмеження |
| --- | --- | --- | --- |
| 0 | Синхронний виклик Vision API з HTTP-обробника | Відсутня інфраструктура черги | Затримка API визначається провайдером; пул з'єднань вичерпується під піком; порушує SRS-NFR-PERF-03 |
| 1 | **BullMQ на Redis** | Офіційний пакет `@nestjs/bullmq`; повторні спроби з експоненційною затримкою, відкладені та періодичні завдання, API стану й прогресу завдання вбудовані; Redis (RESP) уже є в стеку для кешу — єдиний протокол і клієнтська бібліотека | Довговічність визначається персистентністю Redis; семантика «щонайменше одна обробка»; Node.js-специфічний протокол |
| 2 | RabbitMQ (AMQP 0-9-1) | Квоворні черги (Raft) із вищою довговічністю; незалежність від мови споживача; нативний dead-letter exchange | Окремий брокер зі своїм адмініструванням; відкладені повтори потребують плагіна або ланцюжка черг із TTL; відсутній вбудований API стану завдання — статус зберігається окремо; додатковий протокол (AMQP) і клієнтська бібліотека |
| 3 | Amazon SQS | Керована довговічність, вбудований dead-letter і visibility timeout, відсутність адміністрування | Прив'язка до хмарного провайдера (vendor lock-in); оплата за запити; локальне середовище потребує емулятора (LocalStack); суперечить обмеженню розгортання на одному вузлі |
| 4 | Apache Kafka | Висока пропускна здатність, журнал подій | Модель журналу без підтвердження й повтору окремого повідомлення, без затримки повтору; експлуатація кластера непропорційна навантаженню |

## Decision

Обрано варіант 1: **BullMQ на окремому екземплярі Redis**, налаштованому з AOF (`appendonly yes`, `appendfsync everysec`) і політикою `maxmemory-policy noeviction`. Кеш аналітики та лічильники rate limiting розміщуються на іншому екземплярі Redis із політикою `allkeys-lru` (див. [C4 Container](../2_design.md#21-контекстне-та-контейнерне-моделювання-системи-c4-model)).

Обґрунтування за метриками:

1. **Відповідність SRS-NFR-REL-01 без власного коду.** Повторні спроби з експоненційною затримкою, `removeOnFail` і dead-letter реалізуються конфігурацією черги; для RabbitMQ потрібні додатковий плагін або ланцюжок черг із TTL.
2. **Стан завдання (SRS-FUN-04).** BullMQ надає стан і прогрес завдання як частину API; для RabbitMQ потрібна власна таблиця статусів із синхронізацією.
3. **Кількість технологій у стеку.** Redis уже використовується для кешу; BullMQ додає один екземпляр того самого образу й не додає нового протоколу, на відміну від RabbitMQ (AMQP) і SQS (HTTP API провайдера).
4. **Масштабування (SRS-NFR-SCAL-01).** Додаткові споживачі підключаються до тієї самої черги без зміни коду.
5. **Пропускна здатність.** Навантаження на брокер на порядки нижче його можливостей; обмежувальним чинником є Vision API.

Варіанти 3 і 4 відхилено за розгортанням на одному вузлі та непропорційною складністю відповідно; варіант 0 відхилено за порушенням SRS-NFR-PERF-03.

## Consequences

### Позитивні

- Час відповіді API на приймання зображення не залежить від латентності Vision API (SRS-NFR-PERF-03).
- Повтори, затримки та dead-letter налаштовуються конфігурацією.
- Одна технологія зберігання (Redis) для черги й кешу, два незалежні екземпляри з різними політиками пам'яті.
- Відсутні витрати на керовані хмарні сервіси.

### Негативні та ризики

| Ризик | Опис | Компенсація |
| --- | --- | --- |
| Довговічність | За `appendfsync everysec` вікно втрати записів черги — до 1 с; квоворні черги RabbitMQ і SQS такого вікна не мають | Стан завдання зберігається в PostgreSQL як джерело істини; періодичне завдання повертає в чергу завдання зі статусом `queued` старші за 5 хв ([SRS-NFR-REL-06](../srs.md#srs-nfr-rel-06)) |
| Семантика доставки | BullMQ гарантує щонайменше одну обробку; завдання, що «зависло», обробляється повторно | Ідемпотентна обробка за унікальним ключем `job_id` ([SRS-NFR-REL-02](../srs.md#srs-nfr-rel-02)) |
| Неатомарність записів | Запис статусу в PostgreSQL і постановка в Redis виконуються окремо; між ними можливий збій | Узгодження за SRS-NFR-REL-06; Transactional Outbox не застосовується через надмірність для одного вузла |
| Єдина точка відмови | Один екземпляр Redis для черги, реплікація (Sentinel, Cluster) не передбачена | Відновлення з AOF; прийняте обмеження одновузлового розгортання |
| Обмеження payload | Дані черги зберігаються в пам'яті | У завданні передаються ключ об'єкта та ідентифікатори; зображення зберігається в об'єктному сховищі |
| Прив'язка до Node.js | Споживачі іншими мовами не підтримуються; міграція на RabbitMQ або SQS потребує переписування producer і consumer | Робота з чергою ізольована в модулі `RecognitionConsumer` і в точці постановки завдань |
| CI/CD | Інтеграційні тести потребують Redis | Service container у GitHub Actions; тривалість конвеєра контролюється SRS-NFR-INFRA-01 (≤ 10 хв) |
| Ліцензування Redis | Умови ліцензії залежать від версії | Для навчального проєкту обмеження відсутнє; сумісна альтернатива — Valkey |
| FinOps | Витрат на керовані послуги немає; витрати — RAM вузла під чергу | Малий розмір payload; моніторинг глибини черги (SRS-NFR-OBS-02) |
